# 基座与LoRA聊天身份指代对照

2026-11-16，在本机CPU FP32环境检查称呼混淆问题。结论是：本地基座在当前聊天提示下也有同类错误；LoRA在部分明确区分身份的样例上进一步变差，不能把原始问题只归因于微调。

## 对照方式

使用与聊天接口相同的system消息：

> 你是一个乐于助人的助手。请根据对话上下文回答用户的问题。

5组固定问题，每组分别使用贪心解码和temperature=0.7、top_p=0.8、top_k=20的三个采样种子（7、42、2026）。每个条件分别运行基座和LoRA，共40次生成。最大输出96 Token，关闭thinking。

诊断在独立进程运行。加载同一份已校验权重的PeftModel，基座条件临时禁用全部56个LoRA层，LoRA条件全部启用。每一对的提示Token哈希、精度、解码参数和随机种子保持一致，没有修改正在运行的HTTP服务。

原始输出保存在`run/chat_identity_comparison/results.json`，诊断脚本为`scripts/compare_chat_identity.py`。运行记录不提交Git。以下按身份对应和回答完整性人工核对，不使用自动关键词得分；四种解码条件也不是四个独立问题。

## 结果

| 固定问题 | 基座：四种解码 | LoRA：四种解码 |
| --- | --- | --- |
| 用户说“我叫小林”，要求助手介绍自己 | 4次都自称小林 | 4次都自称小林 |
| 历史正确写着“你好，小林！我是一个AI助手”，再问用户姓名 | 4次都回答“我叫小林” | 4次都回答“我叫小林” |
| 历史已包含助手错误自称小林，再问用户姓名 | 4次都沿用错误的第一人称表达 | 4次都误用第一人称或回答助手自己的发言 |
| 明确说“我叫小林，你叫小助手”，要求分别说出两个名字 | 4次都完整、正确对应两个身份 | 1次完整正确，2次漏答用户名字并反问，1次自称两个名字 |
| 用户将称呼从小林改为小周，再问如何称呼 | 4次都正确称呼用户为小周 | 4次都正确称呼用户为小周 |

### 原始问题的贪心输出

输入：

> 你好，我叫小林。请简单介绍一下你自己。

基座和LoRA都输出：

> 你好，我是小林，很高兴认识你！我是你的朋友，有什么可以帮助你的吗？

即使关闭采样，该问题仍然存在。中性、正确的历史也没有消除追问中的指代错误，因此并非只是上一轮错误回复污染了历史。

### 明确区分两个身份的贪心输出

输入：

> 我叫小林，你叫小助手。请分别说出我的名字和你的名字。

基座：

> 我的名字是小助手，你的名字是小林。

LoRA：

> 你好，我是小助手。你叫什么名字呢？

这一例中，基座完成了角色对应，LoRA遗漏了已经提供的用户姓名。相同采样设置下也存在类似差异，说明任务微调会影响部分通用对话表现；这组样例不足以评价整体聊天能力。

## 与当前服务的关系

这组对照使用模型服务的通用聊天提示。当前业务后端的普通聊天使用基座，并显式指定助手身份；金融事件抽取使用LoRA。模型服务的直接聊天接口默认保持LoRA启用。

本记录保留原提示与原始样例结论，不作为当前业务后端身份提示的评估结果。原提示下的基座存在身份指代错误，不能用切换适配器代替对话质量评估。
